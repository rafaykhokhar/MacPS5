# Native Apple Silicon prototype

The Rust executor runs real homebrew startup through an actual load request for `/system/common/lib/libSceSysmodule.sprx`, backed by an explicitly registered native provider. Starting from the ELF entry alone, it automatically compiles twelve additional observed targets while preserving execution state. Guest sandbox/cwd and file metadata calls complete the dependency search. All ten named dependencies now resolve to registered providers. Guest symbol resolution now stops at the unpublished `pthread_create` export after binding seven mutex imports and three thread attribute imports. The error path produces a captured normal exit request with status -1; cleanup remains pending. Game main has not executed. Independently, translated audio calls submit silent PCM through the real Mac audio backend, a Rust graphics queue executes two synthetic command submissions on Metal, and translated VideoOut calls present two synthetic frames and receive completion events under explicit fixture event policy. See [the Rust migration notes](rust/README.md) for coverage; historical milestones below retain their earlier limitations.

Target: user's M5 Pro, with a 16 GB unified-memory design budget. Long-term title goal: Tekken 8. A freely distributed PS5 Crispy Doom homebrew executable is used for loader and translated startup tests. No commercial PS5 game is available or has been tested.

This standalone prototype accompanies the AnyPS5 checkout. It includes a restricted native loader and ARM64 CPU translator, but is not integrated into AnyPS5's runtime. No game reaches gameplay. A new backend reuses AnyPS5's RDNA decoder to translate a limited integer shader subset and single position/color exports to Metal. A bounded PM4 command subset now drives the test draw; full PS5 graphics command processing and game rendering remain unimplemented.

The current Rust-enabled startup harness uses Rust standard/SCE ELF relocation planning through a retained C++ mapping adapter. It executes from the real homebrew ELF entry through successful `__kernel_init`, `__klog_init` and `__patch_init` using an explicitly modeled payload environment. Rust constructs the credential and module-container records, including the observed attribute and patch fields. The fixture uses synthetic process attributes; it does not implement a full PS5 kernel or authorization policy. Startup resolves the Rust implementations of `strcpy`, `strcat`, `strcmp`, `strncmp`, `strlen`, `sprintf`, `calloc`, `free` and `getenv`. The subsequent `__rtld_sprx_init` resolves kernel `sceKernelDlsym`, then fails to resolve `sceKernelLoadStartModule`; its error path reaches unsupported process-name syscall 616 at `0x397`. Rust also handles the existing `snprintf`/`vsnprintf` entry points. The original unavailable-descriptor test remains a separate negative test. Neither path reaches the game's main function.

Rust is now the active CPU translation path and the required language for future implementation work. ELF code extraction, x86 decoding, reachable discovery, ARM64 emission, CPU fixture generation and native CPU test orchestration are implemented in [the Rust crate](rust/README.md). Its native runner executes without Python. Existing C++ runtime and Metal backend code remains during migration, and GPU shaders use Metal Shading Language. The historical Python commands below remain regression references; they do not describe the new active CPU pipeline. The project is not entirely Rust yet.

## Verified milestone

`prototype.py` translates a deliberately restricted set of raw x86-64 leaf functions into ARM64 assembly. Apple's compiler assembles and links them into a native ARM64 Mach-O executable. No Rosetta or x86 interpreter is used in the generated executable.

Supported byte encodings: `89 f8` (mov eax, edi), `b8 imm32` (mov eax, immediate), `01 f0` (add eax, esi), `29 f0` (sub eax, esi), `39 f7` (cmp edi, esi), `0f 42 c6` / `0f 47 c6` / `0f 4c c6` / `0f 4f c6` (unsigned and signed conditional moves from esi to eax), `8b 07` (load eax from [rdi]), `89 37` (store esi to [rdi]), forward short branches `72/73/74/75/76/77/7c/7d/7e/7f`, forward `eb` jumps, and `c3` (ret). Input functions use the x86-64 System V integer argument convention; output functions use Apple's ARM64 integer argument convention. Only a 32-bit return value and explicit stores are observable. Conditions can consume only the flags from the supported comparison. Arithmetic invalidates that comparison state and later conditions are rejected until another comparison. This is not a general implementation of x86 flags.

Verification passed 2,100,475 native CPU checks across arithmetic, signed/unsigned minimum/maximum, all ten supported conditional branches and pointer-based loads/stores, using boundary values and deterministic randomized inputs, plus rejection of sixteen malformed or unsupported inputs. Control-flow validation checks instruction boundaries and defined result/condition state on every reachable path; backward branches, unreachable code and falling outside the function are rejected. Memory access tests use valid host pointers; guest virtual memory, exception behavior, atomics and memory-ordering differences are not implemented. This is a correctness test, not a performance benchmark or general x86 compatibility claim.

Run from the chat workspace:

```sh
python3 outputs/native-apple-silicon/prototype.py --verify work/arm64-prototype
```

Requires ARM64 macOS and Xcode command-line tools. Test artifacts are written under `work/`.

### RDNA integer shader translation to Metal

`rdna_metal.cpp` reuses the unmodified AnyPS5 RDNA decoder at checkout commit `f145139676a48306681d3a4d5fabf83938759daf`. It translates binary VOP1/VOP2 instructions into Metal Shading Language, compiled at runtime and executed by the Apple GPU. The linked decoder remains covered by AnyPS5's GPLv2 license. The prototype builds eight decoder source files directly; it does not require Vulkan or compile the full emulator.

Supported operations are V_MOV_B32, V_NOT_B32, V_ADD_NC_U32, V_SUB_NC_U32, V_SUBREV_NC_U32, V_AND_B32, V_OR_B32, V_XOR_B32, V_XNOR_B32, V_LSHLREV_B32 and V_LSHRREV_B32, followed by S_ENDPGM. Sources include VGPRs, ordinary read-only SGPRs and raw inline/literal constant bits. Arithmetic wraps at 32 bits, shift counts use the low five bits, and inactive lanes preserve their registers. Semantics are based on AMD's [RDNA 2 ISA reference](https://www.amd.com/content/dam/amd/en/documents/radeon-tech-docs/instruction-set-architectures/rdna2-shader-instruction-set-architecture.pdf), VOP1/VOP2 instruction tables (§12.7–12.8), and the local decoder's encoding definitions. No AMD/PS5 hardware comparison has been performed.

This entry point uses an explicit register-state test ABI: input/output arrays of 256 VGPR values per lane, 106 shared SGPR values, a lane count and an active-lane array. It does not implement the PS5 shader launch ABI, EXEC updates, wave communication, GPU memory instructions, textures, floating-point arithmetic, exports or command buffers. Unsupported instructions, SDWA/DPP modifiers, special registers, missing terminators and trailing code throw errors. Source blocks are capped at 4,096 words.

`rdna_metal_verify.mm` feeds synthetic RDNA machine words through that decoder/backend and compares all 256 resulting registers for 1,025 lanes against independent CPU formulas: 262,400 checks, including unchanged registers. Every supported operation is exercised, including overflow, all shift counts modulo 32, scalar/literal inputs, inactive lanes, destination/source aliasing, register dependencies and VGPR255. Additional dispatched guard lanes must leave output canaries unchanged. Eleven malformed or unsupported programs are rejected. These are instruction-semantic checks, not a game shader compatibility test or a speed benchmark.

The complete runner below now includes this path and saves the generated `rdna-generated.metal` under its build directory. The older compute and triangle tests remain useful hardware checks and still use handwritten shaders.

The full suite passed with this backend enabled. A separate AddressSanitizer/UndefinedBehaviorSanitizer build of the native decoder/backend/harness also passed while executing the Metal verification. Those sanitizers cover host code, not GPU shader instructions; GPU results and output bounds are checked by the harness.

### RDNA vertex and pixel exports

`TranslateRdnaRenderBlock` in `rdna_metal.cpp` extends the same decoder and integer emitter with one uncompressed, four-component export per stage: POS0 for a vertex shader, or MRT0 for a pixel shader. It captures source register bits at the export instruction, then returns that captured value through Metal's position or color output. Both stages require DONE, and the pixel export requires VM. Wrong targets, partial masks, compressed data, missing/duplicate exports and unsupported stage encodings throw. Export interpretation follows chapter 11 of the AMD RDNA 2 ISA reference linked above. AMD/PS5 hardware equivalence remains untested.

`rdna_render_verify.mm` renders a triangle using synthetic RDNA vertex/pixel binaries, rather than handwritten vertex/pixel shader bodies. The generated vertex shader reads explicit register banks from the harness (four are supplied; a PM4 vertex offset skips the first); fragment invocations receive a shared initial register bank. Both receive a scalar-register buffer. This remains a test ABI, not the console's vertex-fetch or pixel-input ABI. All shader lanes covered by the draw are active; dynamic EXEC, discarded pixels, interpolation instructions, parameter exports, depth, other render targets and compressed exports are not implemented.

On the M5 Pro the result contains 20,808 colored pixels. A separate CPU half-plane calculation verifies 60,424 interior/background pixel colors away from triangle edges. Nontrivial export register ordering and overwriting source registers after export exercise component mapping and export-time capture. Eight invalid export configurations are rejected. The native decoder/backend/render harness also passed AddressSanitizer and UndefinedBehaviorSanitizer. The generated image is `rdna-triangle.png`; it is a synthetic translated-shader result, not a game screenshot. Draw parameters now come from the PM4 subset described below. Program addresses now come from PM4 shader registers through the registry below. Registration structures, input buffers and raster state are still created by the host harness; this does not validate a game command stream.

### Bounded PM4 draw submission

`pm4.cpp` decodes ordinary type-3 NOP, NUM_INSTANCES, SET_CONTEXT_REG, SET_SH_REG, SET_UCONFIG_REG and DRAW_INDEX_AUTO packets, plus canonical type-2 padding. It retains separate register banks, snapshots their values for each draw, and returns final state for a subsequent submission. Auto draws require explicit instance state and GE_INDX_OFFSET; vertex-range overflow is rejected. Format and draw-state behavior were cross-checked against the checked-out AnyPS5 `Execution/src/Pm4.cpp`, its `Pm4.hpp` packet-length helper and `Graphics/src/State.cpp` triangle-list mapping. Console hardware behavior has not been measured.

Decoding is transactional with respect to the supplied initial state and has no GPU or guest-memory effects. Malformed lengths, unknown opcodes, predicates, compute/custom flags, indexed register banks and unsupported packet types throw with a DWORD position. Limits are 65,536 input words, 512 tracked register entries and 128 draw snapshots. Tests verify immutable per-draw state, consecutive register writes, state across submissions, nonzero vertex offsets, and 17 invalid or over-limit inputs.

The renderer now consumes a synthetic PM4 stream that sets triangle-list topology, GE_INDX_OFFSET=1, one instance and a three-vertex draw. The first input vertex is intentionally outside the triangle and must be skipped. The resulting image still passes 60,424 reference pixel checks. Its render adapter accepts one draw, the four supported program-address registers and the explicit test state; it rejects additional shader/context state, unsupported flags/topologies, extra instances and out-of-bounds vertex ranges. Register parsing alone does not implement their graphics semantics. Render targets, vertex fetching, synchronization, indirect/indexed draws and guest submission imports remain unconnected.

### Shader program-address binding

`shader_registry.cpp` owns immutable copies of registered RDNA shader images. The renderer resolves shader addresses from each PM4 draw's SH-register snapshot, then translates the selected code. Address reconstruction uses the low register shifted by 8 and the validated eight-bit high register shifted by 40. Register pairs 0xc8/0xc9 and 0x08/0x09 follow the local AnyPS5 `PrepareRegistered` mappings for registered type-2 vertex and type-1 pixel shaders; other stage layouts remain unsupported.

Registrations require nonzero 256-byte-aligned addresses within 48 bits, nonempty code of at most 4,096 words, no overlapping images and at most 64 current images. Addresses are guest identifiers, never dereferenced as host pointers. Resolution checks registration bounds and stage. An entry can start at a later 256-byte boundary within an image; decoding and translation subsequently validate its supported instruction stream. Re-registering an address replaces the current image while previously returned draw snapshots retain their original bytes. There is no automatic detection of guest writes or a translated pipeline cache yet.

Tests verify nonzero address-high bits, interior offsets, owned input copies, replacement lifetime and eight invalid bindings. The registry tests also passed AddressSanitizer/UndefinedBehaviorSanitizer. The PM4-to-Metal render test selects both stages through these registers and still passes its 60,424 reference pixel checks. This supplies program binding to the prototype. The header reader below now imports synthetic AGC registration structures through guarded memory; an emulated guest registration-service call remains unconnected.

### Guarded AGC registration-header import

`guest_shader.cpp` reads the 96-byte `Shader` layout defined in the checked-out AnyPS5 `core/libs/SceShaders.hpp`, with compile-time layout checks. It validates magic/version, header length, shader length/alignment and the supported vertex/pixel stage types. Header bytes and code are copied through `GuestMemory` bounds checks; guest pointers are never directly dereferenced. Limits are 64 KiB per header and 16 KiB per code image.

SH/CX register arrays are decoded. Input/output semantics, special-register metadata, user-data metadata and its nested direct/sharp resource arrays must fit inside the copied header. The complete header is retained for later interpretation. Structural validation does not implement resource binding, special-register semantics, scratch, embedded constants or the shader launch ABI. No default resource behavior is synthesized. Registration changes the code registry only after all these checks succeed. This path currently assumes single-threaded guest access; it is not a coherent snapshot mechanism for concurrent guest writes.

`guest_shader_verify.cpp` checks valid nested metadata, owned snapshots and twelve malformed registrations, including invalid pointers, truncated arrays, bad sizes and unsupported stages. Failures leave an existing registered image unchanged. The reader and tests passed AddressSanitizer/UndefinedBehaviorSanitizer. The render harness now places both shader headers/code into guarded guest-memory regions, imports them through this reader, resolves their PM4 program addresses and renders through Metal. It still uses synthetic inputs and host-driven registration, not an emulated `sceAgcDriver` import or a game executable's initialization path.

### Translated CPU call to graphics completion

### Module-qualified native import registry

`elf_image.cpp` collects repeated DT_SCE_NEEDED_MODULE records and rejects duplicate module IDs. `RelocateScoped` passes an `ImportIdentity` containing the original symbol, stripped symbol/NID, owning module, numeric module ID and opaque library token to the resolver. Module IDs use the custom base64 alphabet and 16-bit bound from the checked-out AnyPS5 `domain/ImportModule.hpp`; dependency alias matching follows that implementation. An unmatched module retains its ownership rather than becoming an unscoped search. Unknown IDs, malformed qualification and ambiguous aliases fail without committing relocation patches. The legacy name-only API receives the complete qualified name.

`import_registry.cpp` registers explicit native service addresses under a module and both the plain symbol name and its computed NID. It compiles the original AnyPS5 NID/SHA1 sources directly. Qualified imports cannot fall back to another module. Unqualified imports resolve only when exactly one registered module exports that name. Conflicting registrations fail transactionally. The graphics harness registers only its implemented submission bridge, then links the qualified import before dispatching it.

The fixture computes its NID independently with Python hashlib/base64; C++ computes it using the upstream implementation. `import_verify.cpp` tests their agreement through a real relocation, module isolation, missing exports, exact-name/alias precedence, multiple module records, unresolved metadata retention, and failed-relocation atomicity, with sixteen rejection checks. The complete implemented CPU/homebrew/graphics suite passed on the Apple M5 Pro after this shared-loader change.

This implements module-level lookup for explicit native bridges. Library tokens remain consumer-local opaque metadata: library version matching, loading guest providers, symbol interposition and retail executable containers are not implemented. The SCE-relative table support below is now available within the existing ET_DYN loader. The real homebrew still has 248 unresolved imports and reaches the same console-kernel initialization failure; no game or title performance has been demonstrated.

### SCE-relative dynamic metadata

The native loader now reads SCE string, symbol, RELA and PLT relocation tables from PT_SCE_DYNLIBDATA. Their pointer tags contain offsets relative to that segment's file data; standard dynamic pointers remain guest virtual addresses. Table selection is per tag, permitting mixed standard/SCE metadata while rejecting competing aliases. The tag mapping follows the checked-out AnyPS5 `GuestImageReader.cpp`.

SCE tables must fit their own metadata segment even if more bytes follow in the file. SCE symbol tables require a nonzero, integral declared byte count, and relocation symbol indices must fit it. Duplicate metadata segments, partial dynamic records, incomplete relocation table descriptions, unsupported PLT format, invalid record sizes and arithmetic overflow fail before patch commit. Metadata need not be mapped as guest memory. Guest code remains non-executable on the host; only translated ARM64 runs.

`graphics_elf_fixture.build_sce()` moves its metadata outside all PT_LOAD segments and uses SCE-relative tables, including a valid symbol-table offset of zero. `sce_loader_verify.cpp` verifies this layout, mixed tables, both relocation families, missing imports and 25 rejection cases. The complete implemented regression suite passes, including running this new fixture through qualified NID linking, translated ARM64 CALL, PM4 decoding, RDNA-to-Metal translation, actual M5 Pro rendering and 60,424 reference pixel checks. The standard ELF graphics fixture also still passes.

This extends metadata handling inside the existing ET_DYN loader. It does not add SELF decryption, retail executable types, shared-module lifecycle, TLS, missing PS5 services or title compatibility. The real homebrew startup remains at the documented kernel-environment failure, with 248 unresolved imports.

## Native runtime progress

### Native ELF runtime loader

`elf_image.hpp` and `elf_image.cpp` add a C++20 ET_DYN loader using native macOS virtual memory. It copies PT_LOAD segments, provides zero-filled BSS, reserves gaps, and reads dynamic tables directly from the program headers. Guest x86 code pages never receive native execute permission. The initial loader-owned file-plus-mapping allocation is capped at 256 MiB; this is not a total game-memory guarantee.

Supported relocations are R_X86_64_RELATIVE, R_X86_64_64, R_X86_64_GLOB_DAT and R_X86_64_JUMP_SLOT. Relative and resolved symbol relocations are staged then applied after structural validation; missing symbol relocations remain explicitly unresolved. `ImportsResolved()` is false while any import is missing, and is only a linker-state check, never a claim that an image is executable or a game is playable. IFUNC, TLS, REL/RELR, interpreter loading and oversized alignment are rejected. The bootstrap and bounded service implementations below are available; most imported services remain unimplemented.

`loader_verify.cpp` verifies segment contents, BSS and relocation values against the real PS5 Crispy Doom ELF. All 6,475 relative relocations matched a separate section-table-based checker; 249 imports remain unresolved. The mapping occupies 8,437,760 bytes. Fourteen rejection checks cover malformed bounds, missing imports, repeated relocation and unsupported structures. The loader is independent of the earlier restrictive Python function extractor.

### Executed native startup prefixes

`startup_aot.py` decodes a growing x86-64 subset into ARM64 assembly operating on the explicit register/flags state in `guest_cpu.hpp`. The emitted code runs directly as ARM64; guarded memory access and arithmetic flags use native C++ helpers. This favors correctness over speed at this stage and is not a native-performance claim.

The decoder covers the tested register/memory MOV forms, LEA, PUSH/POP, ADD/SUB/CMP/XOR/INC/TEST, immediate arithmetic, short and near conditional branches, short jumps, and direct/indirect call boundaries. It understands REX register extensions, 32-bit zero-extension, RIP-relative addresses, SIB addressing and signed displacements. Unsupported instructions and branches into instruction interiors fail translation. Prefix mode rejects external branches; resumable region mode can return them to a dispatcher. Calls and returns stop generated code so the runtime can validate guest targets and push/pop guest return addresses. A per-instruction budget stops runaway loops.

The real homebrew checks translate two regions: 23 instructions beginning at `_start` (0x40) and ten instructions beginning at `__crt_syscall_init` (0x3a0). Entering the translated guest call executes the second region, which requests `sceKernelDlsym` through the payload's callback at 0x3c1.

This negative-path test supplies an explicit unresolved callback token, checks the symbol/handle/output-pointer arguments, and verifies that dispatching that token fails without changing the guest stack. `cpu_verify.cpp` covers emitted 32/64-bit arithmetic and flags, extended registers, indexed loads, memory protection and looping instruction limits. `startup_verify.cpp` also exhaustively checks arithmetic flags across 8-bit operand pairs and validates the real startup state. The startup/loader checks passed AddressSanitizer and UndefinedBehaviorSanitizer. MULX now translates 32-/64-bit register and guarded-memory sources to native ARM64 multiplication. Both source values are captured before either destination changes; when the destination registers coincide, the high half is retained. The 32-bit form zero-extends both results, and guest flags remain unchanged. Encoding and semantics follow the [Intel MULX reference](https://cdrdv2-public.intel.com/835752/253667-sdm-vol-2b.pdf). Invalid prefix fields and truncated operands are rejected.

`mulx_verify.cpp` passes 114,688 checks against a bit-serial shift/add reference, including boundary/random operands, implicit-source and destination aliases, extended registers, read-only unaligned sources and failed-read preservation. The sanitizer build passes too; generated assembly is not instrumented. Decoder tests include the actual instruction bytes at homebrew address 0x38fe. This removes the multiplication dependency noted above; mmap/munmap and the remaining environment still prevent the complete symbol resolver and startup from running successfully.

The full CPU/homebrew/Metal regression passes with MULX enabled. This includes the process and module lookup checks added in the preceding milestones; whole-program execution still follows the existing kernel-prerequisite failure path.

### Owned anonymous mappings and complete guest symbol resolution

The callable syscall bridge now handles mmap/munmap (477/73) for anonymous private data mappings. The initial supported policy accepts a zero address hint, MAP_PRIVATE | MAP_ANON (0x1002), read-only or read/write permissions, descriptor -1 and offset zero. It allocates zeroed, 16-KiB-aligned backing, rounds lengths to that modeled page size, and registers access through GuestMemory. These are real owned data buffers; guest requests do not set host mapping flags. Anonymous initialization follows the [mmap contract](https://pubs.opengroup.org/onlinepubs/9799919799/functions/mmap.html); this restricted implementation is not full POSIX or PS5 mmap conformance.

Allocation limits are 16 MiB per mapping, 256 MiB total and 256 live mappings. Whole-allocation unmaps validate the rounded extent, remove the guest region before freeing backing, and update accounting. Invalid, partial or unowned unmaps return EINVAL without changing mappings. Partial unmaps, nonzero hints, fixed/file/shared/executable mappings and protection changes remain unsupported. The owner removes its remaining mappings on destruction. These limits are prototype policy, not evidence that a game's working set fits 16 GB. `GuestMemory::RemoveData` requires an exact region/backing match and refuses executable regions because their removal would need translation invalidation.

`allocation_verify.cpp` executes 17 operations through the real CRT wrapper, checking alignment/rounding, zero contents, writable/read-only behavior, invalid flags/lengths/descriptors, budget and slot limits, stale-pointer rejection, unowned-code preservation and owner cleanup. Byte register/memory CMP decoding was also added for the resolver's NID comparison, using the existing verified byte arithmetic flags implementation.

The real `kernel_dynlib_resolve` at 0x3810 now executes end to end as translated ARM64 against the owned process/module environment. It allocates temporary storage, copies the symbol/string tables through the actual guest kernel-copy helpers, computes the symbol count with MULX, compares NIDs, returns the implemented getpid/__error thunk addresses and frees the temporary mapping. Tests check both registered handles, missing symbols/modules and a failed symbol-table copy; temporary allocated bytes return to zero on each path. No host symbol-resolution shortcut replaces that guest routine. Full process credentials and whole-program kernel initialization remain unfinished, and no game has booted.

Both the allocation and complete-resolver harnesses pass AddressSanitizer/UndefinedBehaviorSanitizer; generated ARM64 assembly is not instrumented. The full CPU/homebrew/Metal regression also passes. Successful isolated resolver execution does not establish successful whole-program initialization.

### Guest snprintf and the next logging dependency

Module 2 now exports an implemented snprintf bridge, also present as a NID symbol in the owned module list. Arguments come from the guest's SysV general-purpose register sequence and then its guarded stack, following the [x86-64 ABI](https://gitlab.com/x86-psABIs/x86-64-ABI/-/blob/master/x86-64-ABI/low-level-sys-info.tex). No guest format or argument pointer is forwarded to host variadic functions.

The initial formatter supports signed/unsigned decimal, octal/hexadecimal, strings, characters, pointers and literal percent; integer length modifiers, width/precision (including starred arguments), padding, alignment and sign/alternate flags are handled. It returns the untruncated length, writes a bounded result plus terminator when capacity is nonzero, and permits zero-capacity length queries without touching the destination. Pointer text uses an explicit 0x hexadecimal policy. Format/input/output work is capped at 65,536 bytes. Floating point, wide strings, locale formatting, positional arguments, %n and vsnprintf remain unsupported. Unsupported formats return -1 with EINVAL, inaccessible memory reports EFAULT, and allocation failure reports ENOMEM. Output is constructed before a guarded write, so these failures preserve the destination.

`format_verify.cpp` checks 43 bridge calls, including independently typed host-reference formatting for integer boundaries, register-to-stack argument transitions, integer narrowing, signed limits, strings, truncation, zero capacity and failure preservation. The sanitizer build passes. The real whole-entry test now resolves snprintf through its own NID/module lookup and then fails on module 2's strerror export. Thus the preceding milestone's missing-snprintf boundary is superseded; no logging call, complete C runtime initialization or gameplay is claimed yet.

The full CPU, whole-entry homebrew, service and Metal regression passes with the snprintf bridge enabled. Sanitizer coverage applies to host bridge code, not generated guest assembly or GPU instructions.

### Guest va_list, error strings and completed logging initialization

Module 2 now also exports vsnprintf and strerror, with matching NIDs in the owned module records. `FormatVaArguments` reads the guest's 24-byte SysV va_list, consumes general-purpose slots up to offset 48 and then follows its overflow argument area. Reads are guarded, arithmetic overflow and malformed general-purpose offsets are rejected, and the cursor is copied so caller storage stays unchanged. The existing integer/string formatter supplies the same supported conversions, truncation and failure behavior. Floating-point slots are not consumed; floating-point and other unsupported formats still return an error. This supersedes the preceding milestone's absence of vsnprintf, without claiming full printf conformance.

strerror returns a guest-readable, read-only buffer owned by the runtime instance. It currently describes the errno values used by the implemented services plus a few common errors; it does not implement the entire console errno table or localization. Other values produce a numeric unknown-error message and set guest EINVAL, following the [FreeBSD unknown-error convention](https://raw.githubusercontent.com/freebsd/freebsd-src/releng/11.0/lib/libc/string/strerror.c). Known values preserve guest errno. Host errno and host error tables are not used. The buffer can be overwritten by the next call in that runtime; guest-thread-local storage remains unfinished.

The formatting/error harness now passes 57 calls, including every aligned general-purpose va_list starting offset, register-to-overflow transitions, unchanged caller storage, malformed offsets, invalid/truncated backing, known/unknown error strings and guest write rejection. Its sanitizer build passes. Whole-entry execution now completes `__klog_init` and verifies all four resolved function slots and its zero return. It then fails the lookup of the __isthreaded data export and attempts to log that diagnostic. The next observed boundary is unsupported syscall 616 at the CRT indirect call (0x397), with the real PID and a writable 32-byte output buffer. No process-name success or log output is fabricated, and gameplay remains unreached.

The whole-entry harness also passes AddressSanitizer/UndefinedBehaviorSanitizer at this new boundary, and the complete CPU/homebrew/Metal regression passes. Sanitizers do not instrument generated guest assembly or GPU instructions.
